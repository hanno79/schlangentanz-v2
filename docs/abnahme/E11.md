### 3. Dauerlauf

`npm run test:dauerlauf` (`vitest run --mode dauerlauf`, vier Dateien `dauerlauf_teil_<n>.dauerlauf.test.ts` zu je 500 Partien): Exit 0, 4/4 grün, 134,4 s (`E11-dauerlauf-lang.txt`). `dauerlauf.test.ts` prüft, dass die vier Teile zusammen 2'000 Partien mit 2'000 verschiedenen Saaten sind, je 1'000 mit und ohne Erweiterung, reihum 2, 3 und 4 Spieler, und dass genau diese vier Dateien existieren.

Am Code nachgesehen, was in jedem Schritt geprüft wird:

- Invarianten und Speichern/Laden: `befundVorDemSchritt` in `testing/dauerlauf.ts` ruft `pruefeSpeichernUndLaden`; das lädt über `deserialisiere`, und das prüft `pruefeInvarianten` und wirft bei einer Verletzung. Die Invarianten werden nur dann einzeln gesucht, wenn Laden scheitert, damit der Befund sie nennt. Damit ist keine Prüfung verloren, sie läuft nur einmal statt zweimal. Der Zustand nach dem letzten Schritt wird vor „beendet“ ebenfalls geprüft.
- Jede aufgezählte Aktion erlaubt: Schleife über alle `motor.aktionen(zustand)` mit `motor.pruefe`.
- Verfälschte Aktion: `verfaelschungsPruefer` wählt je Schritt eine von zehn Verfälschungen (fremder und unbekannter Spieler, anderer Typ, Karte nicht auf der Hand, fehlendes und fremdes Feld, unbekannte Schlange, Stelle ausserhalb, falsche Reaktion, Karte doppelt), verlangt `pruefeAktion` = nicht erlaubt mit Grund und dass `anwendeAktion` mit demselben Grund wirft. `erwarteGeprueftenLauf` verlangt so viele Ablehnungen wie Schritte, `pruefeLangenDauerlauf` dazu alle zehn Arten.
- Handgrenze: `regelPruefer` meldet bei `ZugBegonnen` oder `PartieBeendet` jede Hand über 5 des Spielers, dessen Zug endete.
- Stapel: `stapelPruefer` verlangt „Stapel leer“ genau dann, wenn die Partiephase nicht `Laufend` ist.

Gegenproben (Belege an TF-ENGINE-052): Handgrenze in `zugablauf.ts` auf 6 (Auffüllen und Abwerfen mit `HANDKARTEN + 1`): `npm run test:dauerlauf` Exit 1, 4/4 rot, 2'000 Befunde „A5: Nach dem Zugende hält Spieler 0 6 Karten.“; ebenso `dauerlauf.test.ts` Exit 1.
